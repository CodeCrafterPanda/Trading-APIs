# Zerodha Kite Connect live trading adapter research

Research date: **2026-10-22, Asia/Kolkata**. All links below were accessed on that date. This is documentation research, not account certification. No account credentials, live requests, or orders were used. Fact identifiers Z01–Z34 are stable references for the specification writer. Endpoint examples describe contracts, not application implementation. Sources are limited to Kite Connect v3 documentation, Zerodha product/Z-Connect/support pages, official `zerodha` GitHub SDKs, and Kite forum posts by Zerodha staff; anything else is a gap.

## Which API versions, authentication methods, and account gates apply?

### Takeaway

Kite Connect is a single-version (v3) REST API on `https://api.kite.trade` with form-encoded requests, JSON responses, a daily-expiring access token obtained by SHA-256 checksum exchange, a published per-endpoint rate table and hard per-user order caps. Execution/account APIs are free (Personal app); real-time and historical data need a paid Connect app. Static IP whitelisting applies to order endpoints only.

### Cited Findings

- **Z01 — Version and transport:** v3 requests need `X-Kite-Version: 3`; login URLs need `v=3`; auth moved from query parameters to an `Authorization` header in 3.0. GET/DELETE parameters are query strings; POST/PUT bodies are `application/x-www-form-urlencoded` (margin endpoints are the JSON exception). Success is HTTP 200 with `status: "success"` and `data`; errors are 40x/50x with `status: "error"`, `message`, `error_type`, optional `data`. Timestamps are `yyyy-mm-dd hh:mm:ss` IST (UTC+5.5). Responses may be gzipped; endpoints are not CORS-enabled, so mobile/desktop apps need a backend holding `api_secret`. [Introduction](https://kite.trade/docs/connect/v3/), [Response structure](https://kite.trade/docs/connect/v3/response-structure/), [Changelog](https://kite.trade/docs/connect/v3/changelog/)
- **Z02 — Login flow and checksum:** Redirect to `https://kite.zerodha.com/connect/login?v=3&api_key=xxx` (optional `redirect_params`); Kite returns `request_token` to the registered redirect URL, with a lifetime of "only a few minutes". `POST /session/token` with `api_key`, `request_token`, `checksum` = SHA-256 of `api_key + request_token + api_secret` returns `user_id`, `user_type`, `exchanges`, `products`, `order_types`, `access_token`, `public_token`, `enctoken`, `refresh_token`, `login_time`, `meta.demat_consent`. All later requests use `Authorization: token api_key:access_token`. Prerequisites: active Zerodha account with TOTP 2FA and a developer-console app with a registered redirect URL. [User](https://kite.trade/docs/connect/v3/user/), [Introduction](https://kite.trade/docs/connect/v3/)
- **Z03 — Token lifetime and logout:** `access_token` "expires at 6 AM" the next day as a "regulatory requirement", unless invalidated by `DELETE /session/token?api_key=..&access_token=..` or a Kite Web master-logout. `refresh_token` is "only available to certain approved platforms"; no refresh endpoint is documented. `GET /user/profile` returns identity and `exchanges`/`products`/`order_types` entitlements without tokens. `GET /user/margins[/:segment]` (`equity`|`commodity`) returns `net`, `available` (`cash`, `live_balance`, `collateral`, `intraday_payin`, ...) and `utilised` (`span`, `exposure`, `option_premium`, `m2m_*`, ...). [User](https://kite.trade/docs/connect/v3/user/)
- **Z04 — Rate limits (documented):** Quote **1 req/s**, Historical candle **3 req/s**, Order placement **10 req/s**, all other endpoints **10 req/s**. Also: "limitations at 400 orders per minute and 10 orders per second"; "a single user/API key will not be able to place more than 5000 orders per day" across all segments and varieties; "a maximum of 25 modifications are allowed per order", after which cancel and re-place. 429 is defined only as "Too many requests"; no backoff or headers are documented. [Exceptions](https://kite.trade/docs/connect/v3/exceptions/)
- **Z05 — Pricing tiers:** Product page: Personal tier is **free** ("Full fledged order, GTT, alerts management", margin computation, portfolio); Connect tier is "Full suite of APIs with realtime WebSocket streaming and historical candle data for ₹ 500 / month". Staff statements: Personal apps (March 2025) are free execution/portfolio/funds "minus the market data (both real-time and historical)"; the ₹2000 historical add-on was dropped from February 8, 2025; the Connect fee was cut from ₹2000 to ₹500/month (May 2025) for "the data (real-time + historical) APIs", order/account APIs "free since March 2025"; from October 2026 the ₹500 fee is waived for client IDs with ≥₹2,000 monthly brokerage via developer credits on the 5th. [Product page](https://zerodha.com/products/api), [Z-Connect 24 Apr 2025](https://zerodha.com/z-connect/?p=411859), [Personal APIs (Matti)](https://kite.trade/forum/discussion/comment/49193/), [Historical now free (Matti)](https://kite.trade/forum/discussion/comment/49021/), [Fee revision (Matti)](https://kite.trade/forum/discussion/comment/49590), [Active-user waiver (Nivas)](https://kite.trade/forum/discussion/comment/53067/)
- **Z06 — Static IP and algo rules as implemented:** Support article: "effective 1 April 2026, you must have a static IP for API-based order placement" under NSE/SEBI algo regulations; set under *Profile → IP Whitelist* in the developer console; at least one primary, up to two IPs; "Exchange rules allow just one modification per calendar week"; WebSocket data, order book and positions "can continue to be accessed from any IP address"; family members share one developer account with separate apps and a declaration. Staff forum post (March 2026): orders from unregistered IPs are rejected regardless of frequency; a **10 orders/second** cap returns 429, enforced **per client ID**, and exceeding it requires exchange registration of the strategy; from April 1, `market_protection=0` MARKET/SL-M orders are rejected (`-1` = automatic); MCX has no IOC in the algo segment; keep slicing to 10 slices; Kite Publisher is exempt. The algo ID "tied to the API key" was "the plan for now" (May 2025). [Support: static IP](https://support.zerodha.com/category/trading-and-markets/general-kite/kite-api/articles/static-ip), [Forum: SEBI algo rules (Matti)](https://kite.trade/forum/discussion/comment/52171), [Fee revision thread](https://kite.trade/forum/discussion/comment/49590)
- **Z07 — SDKs:** The docs SDK page lists Python (`zerodha/pykiteconnect`), Go (`zerodha/gokiteconnect`), Java, PHP, Node.js (`kiteconnectjs`) and .NET, all under the `zerodha` GitHub org; the Go README calls itself "The official Go client" with a `ticker` package (`go get github.com/zerodha/gokiteconnect/v4`). The product page also advertises Rust and C++ clients that the SDK page does not list. Any docs page is available as Markdown by appending `.md`; the Agent-setup page defines a `prompt.md` entry point. [SDKs](https://kite.trade/docs/connect/v3/sdks/), [gokiteconnect](https://github.com/zerodha/gokiteconnect), [Product page](https://zerodha.com/products/api), [Agent setup](https://kite.trade/docs/connect/v3/agent-setup/)

### Inferences

- One elected owner performs the daily interactive login, stores `access_token` with `login_time`, and forces renewal before the 06:00 IST boundary. Do not design around `refresh_token`/`enctoken`. Treat any `TokenException`/403 as session-wide (another Kite login can invalidate it): pause submissions, re-login, reconnect sockets, reconcile.
- Register primary and backup egress IPs before enabling execution; the weekly change cap makes IP changes a planned operation. Data and read endpoints may run from elastic infrastructure; order endpoints must egress from the whitelisted address.
- Budget order traffic against 10/s (also the per-client-ID exchange threshold), 400/min and 5000/day, and cap modifications per order locally at 20. Keep 1 req/s quote and 3 req/s historical buckets separate.
- Capability flags per app type: Personal apps disable `quote`, `historical`, `ws`; Connect apps enable them. Prefer Go or Python SDKs as reference; no official Rust SDK is confirmed in the docs listing.

### Gaps

- "6 AM" has no timezone label; no grace period or returned expiry timestamp exists.
- Whether a Personal app receives HTTP postbacks or socket order updates was asked in the staff thread and not answered; billing state, Rust/C++ SDK status and algo-ID scheme need account verification.
- Strategy registration for >10 OPS and whether iceberg legs count toward OPS ("not defined yet" per staff) are undocumented.

## What live streaming, instrument metadata, and data entitlements are documented?

### Takeaway

Kite streams a custom binary protocol (not Protobuf) at `wss://ws.kite.trade` with three fixed packet sizes, five-level depth, caps of 3 connections × 3000 instruments per API key, and text frames carrying order postbacks on the same socket. The instruments master is a daily gzipped CSV without ISIN; REST quotes are snapshots capped at 500/1000 keys and 1 req/s.

### Cited Findings

- **Z08 — Socket, limits, control messages:** `wss://ws.kite.trade?api_key=..&access_token=..`. "You can subscribe for up to 3000 instruments on a single WebSocket connection"; "Single API key can have upto 3 websocket connections." Control JSON: `{"a":"subscribe"|"unsubscribe","v":[tokens]}`, `{"a":"mode","v":["ltp"|"quote"|"full",[tokens]]}`. [WebSocket](https://kite.trade/docs/connect/v3/websocket/)
- **Z09 — Frame and packet layout:** A frame is int16 packet count, then per packet an int16 length and the packet; frames carry many instruments. Modes: `ltp` **8 bytes**, `quote` **44**, `full` **184**. Offsets (int32): 0 token, 4 LTP, 8 last traded qty, 12 ATP, 16 day volume, 20 total buy qty, 24 total sell qty, 28 open, 32 high, 36 low, 40 close (quote ends at 44), 44 last-traded timestamp, 48 OI, 52 OI day high, 56 OI day low, 60 exchange timestamp, 64–184 depth: ten 12-byte entries (five bids then five offers) of `quantity` int32, `price` int32, `orders` int16, 2 padding bytes. [WebSocket](https://kite.trade/docs/connect/v3/websocket/)
- **Z10 — Index packets:** Indices "such as NIFTY 50 and SENSEX differ from that of tradeable instruments. They have fewer fields": 0 token, 4 LTP, 8 high, 12 low, 16 open, 20 close, 24 price change (quote mode ends; 28 bytes), 28 exchange timestamp (full; 32 bytes). [WebSocket](https://kite.trade/docs/connect/v3/websocket/)
- **Z11 — Price scaling:** "All prices are in paise." Currencies: divide int32 prices by **10000000** (four decimals); "For everything else, the price values should be divided by 100." No segment IDs on the page. The official Python client uses `segment = instrument_token & 0xff` with map nse=1, nfo=2, cds=3, bse=4, bfo=5, bcd=6, mcx=7, mcxsx=8, indices=9; divisor 10^7 for CDS, **10^4 for BCD**, 100 otherwise; `tradable=False` for segment 9; both timestamps parsed as unsigned 32-bit Unix seconds. [WebSocket](https://kite.trade/docs/connect/v3/websocket/), [pykiteconnect ticker.py](https://raw.githubusercontent.com/zerodha/pykiteconnect/master/kiteconnect/ticker.py)
- **Z12 — Heartbeat and text frames:** With no data pending, a 1-byte heartbeat is sent "every couple of seconds" and "can be safely ignored". Text frames are JSON `{"type","data"}` with `order` (full postback payload), `error` and `message`. "Market data is always binary and Postbacks and other updates are always text." The docs say nothing on reconnection or token-expiry disconnects; the Python client defaults are `RECONNECT_MAX_DELAY=60`, `RECONNECT_MAX_TRIES=50` (max 300, min delay 5), `CONNECT_TIMEOUT=30`, with `on_order_update`, `on_reconnect`, `on_noreconnect` callbacks. [WebSocket](https://kite.trade/docs/connect/v3/websocket/), [pykiteconnect ticker.py](https://raw.githubusercontent.com/zerodha/pykiteconnect/master/kiteconnect/ticker.py), [pykiteconnect v4 docs](https://kite.trade/docs/pykiteconnect/v4/)
- **Z13 — Instruments master:** `GET /instruments` and `GET /instruments/:exchange` return a gzipped CSV generated once a day; fetch "ideally around 08:30 AM" and store. Columns: `instrument_token`, `exchange_token`, `tradingsymbol`, `name`, `last_price` (stale), `expiry`, `strike`, `tick_size`, `lot_size`, `instrument_type` (EQ/FUT/CE/PE), `segment` (NSE, NFO-FUT, NFO-OPT, MCX, ...), `exchange`. **No ISIN column.** Key on `exchange:tradingsymbol`; exchanges reuse `instrument_token` for derivatives after expiry. Exchange enumerations elsewhere: orders accept NSE, BSE, NFO, CDS, BCD, MCX; alerts add INDICES; BFO is segment 5 in the SDK map. [Market quotes and instruments](https://kite.trade/docs/connect/v3/market-quotes/), [Orders](https://kite.trade/docs/connect/v3/orders/), [Alerts](https://kite.trade/docs/connect/v3/alerts/)
- **Z14 — REST quotes:** Repeated `i=exchange:tradingsymbol` keys (spaces as `+`, e.g. `NSE:NIFTY+50`); missing keys are silently omitted. `/quote` ≤ **500**: `timestamp`, `last_trade_time`, `last_price`, `last_quantity`, `buy_quantity`, `sell_quantity`, `volume`, `average_price`, `oi`, `oi_day_high`, `oi_day_low`, `net_change`, `lower_circuit_limit`, `upper_circuit_limit`, `ohlc`, five-level `depth`. `/quote/ohlc` ≤ **1000**; `/quote/ltp` ≤ **1000**. Quotes are snapshots "taken at request time". No IV or Greeks fields. [Market quotes and instruments](https://kite.trade/docs/connect/v3/market-quotes/)
- **Z15 — Data entitlement:** Personal apps exclude real-time and historical data (users report `Insufficient permission for that call` on quote calls); Connect apps include streaming and historical. [Personal APIs (Matti)](https://kite.trade/forum/discussion/comment/49193/), [Product page](https://zerodha.com/products/api)

### Inferences

- Universe capacity is a hard budget of 3 × 3000 slots per API key. Reserve in order: positions/working orders and execution candidates in `full`, scanner coverage in `quote`, remainder in `ltp`.
- Implement the decoder from the documented offsets with a `token & 0xff` segment switch and divisors 100 / 10^7 CDS / 10^4 BCD; the BCD divisor and index detection are SDK-derived, so unit-test against captured frames and label the evidence class. Treat both timestamps as Unix seconds and keep them distinct; derive interval volume from day-volume deltas, never by summing `last_traded_quantity`.
- Socket `order` text frames are the primary live order feed; dedupe against HTTP postbacks (Z25) and order-history polls.
- The daily CSV is the only derivative discovery source: cache every day's file (expired tokens are otherwise irrecoverable, Z17) and derive option chains by filtering `*-OPT` segments on `name`, `expiry`, `strike`, `instrument_type`. Canonical identity is `exchange:tradingsymbol`; cross-exchange equity equivalence needs `isin` from holdings (Z29) or an external master.

### Gaps

- No reconnect policy, socket behaviour at 06:00 expiry, subscription persistence after reconnect, or whether the 3-connection cap spans apps.
- No full supported-exchange list on the instruments page; no `freeze_quantity`, ISIN, underlying or weekly flags in the CSV.
- No sequence numbers, replay, latency bound or every-trade delivery guarantee; `/quote` behaviour for INDICES keys is unstated.

## Which historical and options APIs support live intelligence?

### Takeaway

Historical candles are REST-only with eight intervals, per-request day caps published by staff rather than the reference, optional OI, and a daily-only `continuous` mode for expired futures. There is no option-chain, IV or Greeks endpoint; chains are built from the CSV plus `/quote` or socket slots.

### Cited Findings

- **Z16 — Endpoint:** `GET /instruments/historical/:instrument_token/:interval` with `from`/`to` as `yyyy-mm-dd hh:mm:ss`, `continuous` 0/1, `oi` 0/1. Intervals: `minute`, `3minute`, `5minute`, `10minute`, `15minute`, `30minute`, `60minute`, `day`. Records are `[timestamp, open, high, low, close, volume]` with OI appended when `oi=1`; timestamps carry `+0530`. Sub-day windows are allowed. Rate limit 3 req/s (Z04). [Historical](https://kite.trade/docs/connect/v3/historical/)
- **Z17 — Continuous data:** "exchanges flush the `instrument_token` for futures and options contracts for every expiry"; the master "only returns instrument_tokens for contracts that are live"; expired tokens are unrecoverable "unless you regularly download and cache them". `continuous=1` "works for NFO and MCX futures contracts" and returns **`day` candle records** for the expired contracts of the same underlying. Staff: intraday data exists for active options but not expired ones; expired futures have daily candles only; no extra charge for options history. [Historical](https://kite.trade/docs/connect/v3/historical/), [Historical now free thread](https://kite.trade/forum/discussion/comment/49021/)
- **Z18 — Per-request range caps (staff, not reference):** sujith (Jan 2018, edited May 2020): minute **60 days**, 3minute **100**, 5minute **100**, 10minute **100**, 15minute **200**, 30minute **200**, 60minute **400**, day **2000** days. The docs page has no range table, no subscription note, no index-support statement and no adjustment policy. [Forum: candle cap (sujith)](https://kite.trade/forum/discussion/3105/historical-api-frequency-and-limit-on-number-of-candles-fetched), [Historical](https://kite.trade/docs/connect/v3/historical/)
- **Z19 — No options analytics:** The v3 navigation (Introduction, Agent setup, SDKs, Response structure, User, Orders, GTT, Alerts, Portfolio, Market quotes, WebSocket, Historical, Postbacks, Mutual funds, Margin calculation, Publisher, Mobile apps, Changelog) has no option-chain, Greeks, IV, PCR or expiry-list endpoint; quote and socket payloads expose only `oi`, `oi_day_high`, `oi_day_low`. [Exceptions (nav)](https://kite.trade/docs/connect/v3/exceptions/), [Market quotes](https://kite.trade/docs/connect/v3/market-quotes/), [WebSocket](https://kite.trade/docs/connect/v3/websocket/)

### Inferences

- Chunk backfill by the Z18 caps, treat them as mutable staff guidance (detect truncation and halve the window), stay under 3 req/s, and parallelise across instruments. Store one-minute canonical candles and aggregate locally; use native coarser intervals as cross-checks.
- `continuous` is a daily stitched series across rolls with no documented adjustment; never use it intraday. Maintain a dated contract registry from daily CSVs.
- Option chain = CSV join plus `/quote` batches of ≤500 at ≤1 req/s or socket slots. IV, Greeks, PCR, OI buildup and liquidity scores are internal models; Kite supplies none.
- Validate index history empirically in read-only certification before relying on it.

### Gaps

- Data start dates, corporate-action adjustment, current-candle semantics, volume units and index coverage are undocumented; Z18 caps are 2018/2020 statements to re-measure.

## Which execution, portfolio, risk and rate-limit contracts are documented?

### Takeaway

Kite offers five varieties, four products, four order types, TTL validity, mandatory market protection on MARKET/SL-M, server-side iceberg and autoslice, GTT single/OCO, alert-to-order, checksum-signed postbacks mirrored on the socket, SPAN/basket margin calculators and a fixed exception taxonomy. There is no kill switch, no idempotency key and no bracket order.

### Cited Findings

- **Z20 — Placement:** `POST /orders/:variety`, `variety` ∈ `regular`, `amo`, `co`, `iceberg`, `auction`; `exchange` ∈ NSE, BSE, NFO, CDS, BCD, MCX; `order_type` MARKET, LIMIT, SL, SL-M; `product` CNC, NRML, MIS, MTF (added 2025-01-17); `validity` DAY, IOC, TTL with `validity_ttl` = "Order life span in minutes"; `disclosed_quantity` (equities only), `iceberg_legs` ("between 2 and 50"), `iceberg_quantity` (= quantity/legs), `auction_number`, `market_protection`, `autoslice` (default false), `tag` ("alphanumeric, max 20 chars"). Returns `order_id`; "This does not guarantee the order's receipt at the exchange." Iceberg/TTL added 2022-03-19; auction 2022-12-22. [Orders](https://kite.trade/docs/connect/v3/orders/), [Changelog](https://kite.trade/docs/connect/v3/changelog/)
- **Z21 — Market protection and autoslice:** `market_protection` applies only to MARKET and SL-M (>0–100 percent within circuit limits, or `-1` automatic); it "converts market orders to limit orders" but execution "remains subject to exchange-defined LPP ranges". `autoslice=true` splits above freeze limits into child orders with their own `order_id`; "The maximum number of slices generated from a single auto slice order is 10"; success and `error` objects (`code`, `error_type`, `message`, `data`) can coexist (text says `data` is an array; the example shows `children`). [Orders](https://kite.trade/docs/connect/v3/orders/)
- **Z22 — Modify/cancel/lookup:** `PUT /orders/:variety/:order_id` (regular: `order_type`, `quantity`, `price`, `trigger_price`, `disclosed_quantity`, `validity`, example also sends `market_protection`; CO: `price`, `trigger_price`; second-leg CO may need `parent_order_id`). `DELETE /orders/:variety/:order_id`. `GET /orders`, `GET /orders/:order_id` (state history), `GET /trades`, `GET /orders/:order_id/trades`. Fields include `exchange_order_id` (null if never at exchange), `parent_order_id`, `placed_by`, `guid` ("Unusable request id to avoid order duplication"), `status_message_raw`, `filled_quantity`, `pending_quantity`, `cancelled_quantity`, `order_timestamp`, `exchange_timestamp`, `exchange_update_timestamp`, `meta`. [Orders](https://kite.trade/docs/connect/v3/orders/)
- **Z23 — Statuses:** Common OPEN, COMPLETE, CANCELLED, REJECTED; transient (non-exhaustive) PUT ORDER REQ RECEIVED, VALIDATION PENDING, OPEN PENDING, MODIFY VALIDATION PENDING, MODIFY PENDING, TRIGGER PENDING, CANCEL PENDING, AMO REQ RECEIVED; MODIFIED in history. [Orders](https://kite.trade/docs/connect/v3/orders/)
- **Z24 — GTT:** `POST /gtt/triggers` with `type` `single` (one trigger value, first order fires) or `two-leg` ("implements the OCO (One Cancels Other) order": two values, the matching order fires, the other stays dormant); `condition` (`exchange`, `tradingsymbol`, `trigger_values`, `last_price` at placement); `orders` array indexed to trigger values, each with `order_type` (only `LIMIT` documented), `product`, `price`, `quantity`. `GET /gtt/triggers` lists active plus other states from the previous 7 days; `GET/PUT/DELETE /gtt/triggers/:id`. Statuses: active, triggered, disabled, expired, cancelled, rejected, deleted. Samples show `expires_at` one year after `created_at`; no rule is stated. [GTT](https://kite.trade/docs/connect/v3/gtt/)
- **Z25 — Postbacks:** POST JSON (raw body) to the app's registered `postback_url` on COMPLETE, CANCEL(LED), REJECTED and UPDATE (modify or partial fill); only orders placed with that `api_key`; sent even when logged out; "reliably", no retry policy. `checksum` = SHA-256 of `order_id + order_timestamp + api_secret` (table says `timestamp`). Payload adds `user_id`, `app_id`, `unfilled_quantity`, `guid`, `market_protection`. Individual developers are told to prefer WebSocket order updates, which also cover Kite web/mobile orders. [Postbacks](https://kite.trade/docs/connect/v3/postbacks/), [WebSocket](https://kite.trade/docs/connect/v3/websocket/)
- **Z26 — Alerts:** `POST/GET/PUT/DELETE /alerts` (2025-06-12); `type` `simple` or `ato` (basket JSON whose item `params` include `variety`, `validity_ttl`, `iceberg_legs`, `market_protection`, `squareoff`, `stoploss`, `trailing_stoploss`); `lhs_exchange` ∈ NSE, BSE, NFO, CDS, BCD, MCX, INDICES; operators `<=,>=,<,>,==`; `rhs_type` constant or instrument; **500 active alerts per user**; `GET /alerts/{uuid}/history`. [Alerts](https://kite.trade/docs/connect/v3/alerts/)
- **Z27 — Margins and charges:** JSON `POST /margins/orders[?mode=compact]` (per order `span`, `exposure`, `option_premium`, `additional`, `bo`, `cash`, `var`, `pnl`, `leverage`, `charges`, `total`, considering positions and open orders); `POST /margins/basket?consider_positions=..[&mode=compact]` returns `initial`, `final` (spread benefit), `orders`, `charges` (basket-level charges "can be ignored" when STT/CTT mix; use per-order); `POST /charges/orders` virtual contract note (brokerage, STT/CTT, stamp duty, exchange/SEBI turnover, GST) with any `order_id` and non-zero `average_price`. No basket size cap stated. [Margins](https://kite.trade/docs/connect/v3/margins/)
- **Z28 — Positions:** `GET /portfolio/positions` returns `net` and `day` arrays (`product`, `quantity`, `overnight_quantity`, `multiplier`, `average_price`, `last_price`, `pnl`, `m2m`, `unrealised`, `realised`, buy/sell and day-buy/sell breakdowns). `PUT /portfolio/positions` converts product (`position_type` `day`|`overnight`, `old_product`, `new_product`). No exit endpoint: exit by an opposite order with the same `product`. [Portfolio](https://kite.trade/docs/connect/v3/portfolio/)
- **Z29 — Holdings:** `GET /portfolio/holdings` includes `isin`, `t1_quantity`, `realised_quantity`, `used_quantity`, `authorised_quantity`, `collateral_quantity`, `discrepancy`, `pnl`, `day_change` and an `mtf` block. `GET /portfolio/holdings/auctions` adds `auction_number`. `POST /portfolio/holdings/authorise` returns `request_id`; the user completes CDSL authorisation at `https://kite.zerodha.com/connect/portfolio/authorise/holdings/:api_key/:request_id`; valid until 17:30; unauthorised sells return HTTP **428**. [Portfolio](https://kite.trade/docs/connect/v3/portfolio/)
- **Z30 — Exceptions:** `TokenException` (403, incl. login elsewhere), `UserException`, `OrderException`, `InputException` (400), `MarginException`, `HoldingException`, `NetworkException` (OMS unreachable), `DataException`, `GeneralException`; HTTP 400/403/404/405/410/429/500/502/503/504. [Exceptions](https://kite.trade/docs/connect/v3/exceptions/)

### Inferences

- Manifest: `regular` for working orders, `amo` after hours, `iceberg` (2–50 legs) or `autoslice` (≤10) above freeze limits, GTT `two-leg` for resting OCO exits, `co` only if certified. Always send `market_protection` (−1 or validated percent) on MARKET/SL-M; default to LIMIT/SL.
- Write a durable intent record before each POST; on timeout query `GET /orders` and match by `tag` (≤20 alphanumeric, used as intent ID) before any retry. `guid` is not a client idempotency key.
- Accept HTTP postbacks only after checksum verification with the server-held `api_secret`; socket `order` frames are the low-latency feed and also see manual Kite-app interventions; reconcile both against order history. The 25-modification cap means trailing logic is cancel/replace or GTT modification.
- Call `/margins/basket` with `consider_positions=true` before multi-leg entries and `/charges/orders` for net-P&L; cache with generation IDs.
- No broker kill switch: the application cancels open orders and sends opposite-side protected orders within 10/s and 400/min, then verifies positions.

### Gaps

- No kill-switch, bracket (`bo`), trailing-stop or basket-placement endpoint; `squareoff`/`stoploss`/`trailing_stoploss` appear only inside alert baskets.
- TTL min/max, GTT count/expiry/MARKET support, CO and MTF eligibility, postback retry policy and the autoslice response shape need account certification.
- Trade responses show `filled` vs `quantity`, and CANCEL vs CANCELLED spelling differs; normalise defensively.

## How should implementation prove the adapter is usable without inventing capabilities?

### Takeaway

The documentation supports a full execution-plus-data adapter, but several operational rules (token boundary, static IP, order caps, day-range caps, BCD divisor) come from support articles, staff posts or SDK code rather than the reference. Each must be stored as evidence with its source class and re-verified.

### Inferences

Required acceptance evidence, as engineering design rather than broker promises:

1. Download `/instruments` daily; validate columns, confirm no ISIN, map segments by `token & 0xff`, retain dated snapshots, reject duplicate `exchange:tradingsymbol` keys.
2. Complete redirect login with checksum exchange; store `login_time`; prove `DELETE /session/token` invalidates and a stale token yields `TokenException`; compare `profile` entitlements to the manifest.
3. Open one socket; subscribe in all three modes plus an index token; decode 8/28/32/44/184-byte packets against captured frames; assert divisors per segment; observe heartbeats and a text `order` frame; probe the 3-socket and 3000-instrument caps.
4. Fetch each interval at the Z18 boundary and one day beyond; record truncation; confirm the `oi=1` seventh column and daily-only `continuous`.
5. Build a chain for one NSE and one BSE underlying from CSV plus `/quote` within 1 req/s; verify `oi` fields and absence of Greeks.
6. Exercise the three margin/charges endpoints with fixtures, including compact mode.
7. Verify postback checksums with a known secret on captured payloads; confirm socket order frames share the schema; dedupe by `order_id` + `exchange_update_timestamp`.
8. Only after static IP registration, operator authorisation and regulatory gates: bounded live commissioning of LIMIT, SL, protected MARKET, modify (≤25), cancel, iceberg, autoslice, GTT single/OCO, position conversion, and 429 behaviour under 10/s and 400/min.
9. Record dated conformance evidence per endpoint, source class and account; block only the affected capability when a check fails.

## Comparison hooks vs Dhan/Upstox

- Kite HTTP postbacks are **checksum-signed** (SHA-256 of `order_id + order_timestamp + api_secret`); the inspected Upstox webhook has no signature. Kite also mirrors order updates as text frames on the market-data socket.
- Kite has **no option-chain, Greeks, IV or PCR endpoint**; Upstox documents a chain with Greeks. Kite chains are built from the CSV plus `/quote` (≤500 keys, 1 req/s) or socket slots.
- Kite streaming is a hand-rolled **binary protocol** (8/44/184-byte packets, 28/32-byte index packets), not Protobuf; caps are **3 sockets × 3000 instruments per API key** versus Upstox's per-user mode-dependent limits.
- Kite historical data needs the paid **Connect** app (₹500/month, waived for ≥₹2,000 monthly brokerage from October 2026); execution and portfolio APIs are free. Range caps are staff-published per interval (minute 60 days … day 2000 days).
- Kite GTT offers **single and two-leg OCO** triggers with LIMIT orders only; Upstox GTT documents ENTRY/TARGET/STOPLOSS rules and a beta trailing gap.
- Kite exposes **basket margin with spread benefit** and a virtual contract note; Upstox documents a per-instrument margin calculator.
- Kite supports server-side **iceberg (2–50 legs)**, **autoslice (≤10)**, **TTL validity**, **auction** variety and **alert-to-order** (500 active alerts); Upstox documents slicing and ≤10-order batches.
- Kite has **no kill-switch API**, no bracket order and no idempotency key; Upstox documents a segment kill switch with a 12-hour cooling period.
- Kite's instruments CSV lacks ISIN (holdings carry it); Upstox's BOD JSON includes ISIN and freeze quantity.
- Kite documents hard order caps (**10/s, 400/min, 5000/day, 25 modifications per order**) and a 1 req/s quote limit; static IP applies only to order endpoints with one whitelist change per calendar week.
