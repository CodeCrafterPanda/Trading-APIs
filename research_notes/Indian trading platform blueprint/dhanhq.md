# DhanHQ live platform API research

Research accessed 2026-10-21; planning reference timezone Asia/Kolkata. Public documentation only; no credentials, account access, orders, subscription purchase, or application implementation. Fact IDs identify documented claims; inferences are engineering recommendations and gaps are launch verification requirements.

## Which versions, identity, entitlements and limits apply?

### Takeaway
Dhan's substantive public API reference is v2, with release notes through feature release 2.5. Authentication, account data entitlement and static egress addressing are separate prerequisites.

### Cited Findings
- **D01 — Documentation location:** Both user-supplied URLs returned the same generic developer landing page rather than endpoint specifications during this research. The substantive reference is the other official host below. [Requested trading URL](https://docs.dhanhq.co/api/v2/trading-apis), [requested data URL](https://docs.dhanhq.co/api/v2/data-apis), [substantive reference](https://dhanhq.co/docs/v2/).
- **D02 — Version chronology:** API route namespace remains `/v2`; release 2.5 is dated 2026-02-09. Release 2.4 introduced 24-hour tokens and static IP requirements for order creation, modification and cancellation. Release 2.3 reduced order throughput to 10/second. Release 2.2 expanded intraday history from the older five-day offering to five years. Therefore the old five-day statement is superseded, not an unresolved present-day alternative. The same release page specifies modification quantity as total placed quantity, rather than remaining quantity. [Release notes](https://dhanhq.co/docs/v2/releases/).
- **D03 — Authentication and entitlement:** Trading APIs are free; Data APIs have separate charges. Web-generated access tokens last 24 hours. TOTP-enabled accounts can generate tokens via `POST https://auth.dhan.co/app/generateAccessToken` with client ID, PIN and TOTP. `GET /v2/RenewToken` renews only active tokens originally generated from Dhan Web, invalidating the old token; expired tokens cannot renew. Individual API-key/secret credentials last 12 months; consent, browser login/2FA and token exchange form the alternative login flow. A maximum 25 consent IDs/day is documented. `GET /v2/profile` reports token expiry, activated segments, Data API status/expiry and DDPI. Primary/secondary static IPv4 or IPv6 addresses can be registered; each individual requires unique static IPs; changes lock for seven days. IP endpoints are `POST /ip/setIP`, `PUT /ip/modifyIP`, `GET /ip/getIP`. Read-only order/trade retrieval does not require this IP registration. [Authentication](https://dhanhq.co/docs/v2/authentication/).
- **D04 — Current reference limits:** Order API ceilings: 10 requests/second, 250/minute, 1,000/hour, 7,000/day. Data API ceilings: 5/second and 100,000/day; minute/hour cells are unspecified. Quote APIs: 1/second; non-trading APIs: 20/second. Reference marks longer windows unlimited for quote/non-trading categories. Each order allows at most 25 modifications. Error envelope uses `errorType`, `errorCode`, `errorMessage`. [Introduction and limits](https://dhanhq.co/docs/v2/).
- **D05 — Marketing conflict:** The marketing page advertises Data APIs at ₹499, but also contains older throughput claims of 25 orders/second and 5,000/day. Treat its price as indicative only; do not use these older execution limits. Confirm current billing period, tax and account price in the broker console. [Marketing/pricing](https://dhanhq.co/trading-apis).

### Inferences
- Model `auth_method`, `token_origin`, `expires_at`, `data_entitlement_expires_at`, enabled segments and whitelisted egress addresses independently. Do not apply Web-token renewal to an OAuth/API-generated token without documented confirmation.
- Use one credential coordinator per broker account. Rotate credentials under an account lock, then reauthenticate streams and reconcile execution state. Never log query strings containing token, PIN or TOTP; the documented endpoints put sensitive fields in URLs.
- Treat rate ceilings as account-wide conservative shared budgets, across processes and strategies. Apply all documented windows, not only per-second throughput. Reserve budget for protective modifications/cancellations. The 7,000/day constraint is a broker boundary, not an arbitrary platform trade cap.
- Capability and restriction metadata must be configurable, source-dated and checked before enabling an account. No automatic permission or price assumptions.

### Gaps
- The introductory rate table does not precisely define fixed/sliding window reset semantics, endpoint-category membership, counting of sliced children, or whether failed requests consume all budgets. The annexure describes per-user throttling, so account-scoped enforcement is the safe design; verify details with Dhan.
- Actual subscription fees, 20/200-depth entitlements, contract access and account-specific limits require console/broker confirmation. Retail access does not establish redistribution/display licensing rights for other users.
- General order-type enums are not proof that every order type remains permitted for every algorithm, product or segment under current exchange/broker controls. Use the compliance research and broker acceptance matrix as additional gates.

## What live, historical and instrument data is actually documented?

### Takeaway
Normal market feed uses JSON subscription commands and little-endian binary responses. Quote/full packets carry more than LTP; sparse ticker mode alone cannot support volume-based intelligence.

### Cited Findings
- **D06 — Normal feed:** `wss://api-feed.dhan.co?version=2&token=…&clientId=…&authType=2`; five connections/user, 5,000 subscriptions/connection, maximum 100 instruments/JSON subscription message. Requests identify `ExchangeSegment` and `SecurityId`. Binary header is eight bytes: response code, length, segment, security ID. Ticker carries LTP/LTT; quote adds last quantity, average traded price, cumulative volume, total buy/sell quantity and daily OHLC; separate packets provide previous close/previous OI and current OI. Full mode combines quote, OI and five depth levels. Depth has bid/ask prices, quantities and order counts. Server ping cadence is ten seconds; no pong for over forty seconds disconnects. Creating more than five connections displaces the first with code 805. LTT is epoch time. [Live market feed](https://dhanhq.co/docs/v2/live-market-feed/).
- **D07 — Feed enums:** Subscription/unsubscription codes are ticker 15/16, quote 17/18 and full 21/22; full-depth 23/24. Relevant segment codes: `IDX_I=0`, `NSE_EQ=1`, `NSE_FNO=2`, `BSE_EQ=4`, `BSE_FNO=8`. `INTRADAY` covers equities and F&O; `MARGIN` means F&O carryforward; `CNC` means equity delivery. [Annexure](https://dhanhq.co/docs/v2/annexure/).
- **D08 — Dedicated deep feeds:** Only NSE equity/derivatives are documented for full depth. Twenty-level endpoint is `wss://depth-api-feed.dhan.co/twentydepth`; maximum 50 instruments/connection and 50/request. Two-hundred-level endpoint is `wss://full-depth-api.dhan.co/twohundreddepth`; one instrument/connection. Both authenticate with token/clientId/authType query parameters. Deep packets use a 12-byte header and separate bid/ask arrays; depth rows contain float64 price and uint32 quantity/order count. Messages can concatenate multiple packets, requiring length-based iteration. Twenty-level header's sequence is explicitly labelled to be ignored; 200-level header carries row count. Prose incorrectly reverses bid/ask labels in places; packet tables label 41 as buy/bid and 51 as sell/ask. [Full market depth](https://dhanhq.co/docs/v2/full-market-depth/).
- **D09 — REST snapshots:** `POST /marketfeed/ltp`, `/marketfeed/ohlc`, `/marketfeed/quote` accept segment-to-security-ID arrays; maximum 1,000 instruments/request at one request/second. Quote provides depth, OHLC, OI and volume. These are snapshots, not a stream replacement. [Market quote](https://dhanhq.co/docs/v2/market-quote/).
- **D10 — History:** `POST /charts/historical` returns daily OHLCV back to instrument inception, with optional derivative OI; its `toDate` is explicitly exclusive. `POST /charts/intraday` documents active instruments across exchanges/segments, five years of OHLCV/OI, minute intervals **1, 5, 15, 25, 60**, and maximum 90 days/request. Request identity fields: `securityId`, `exchangeSegment`, `instrument`; intraday adds `interval`, date-times and optional `oi`; daily permits `expiryCode`. Responses are parallel OHLCV/timestamp arrays, timestamps epoch seconds. [Historical data](https://dhanhq.co/docs/v2/historical-data/).
- **D11 — Instrument sources:** Compact CSV is `https://images.dhan.co/api-data/api-scrip-master.csv`; detailed CSV is `https://images.dhan.co/api-data/api-scrip-master-detailed.csv`; segment retrieval is `GET /v2/instrument/{exchangeSegment}`. Documented metadata include exchange/segment, ISIN, underlying security ID/symbol, instrument type, series, lot size, expiry, strike, CE/PE, tick size, weekly/monthly expiry, cover/bracket permissions and surveillance flags. [Instrument list](https://dhanhq.co/docs/v2/instruments/).
- **D12 — Live CSV header observation:** On the research date, a read-only ranged fetch of the detailed master verified `SECURITY_ID`, `EXCH_ID`, `SEGMENT`, `ISIN`, `INSTRUMENT`, `UNDERLYING_SECURITY_ID`, `UNDERLYING_SYMBOL`, `SYMBOL_NAME`, `DISPLAY_NAME`, `INSTRUMENT_TYPE`, `SERIES`, `LOT_SIZE`, `SM_EXPIRY_DATE`, `STRIKE_PRICE`, `OPTION_TYPE`, `TICK_SIZE`, `EXPIRY_FLAG`, `BRACKET_FLAG`, `COVER_FLAG`, `ASM_GSM_FLAG`, `ASM_GSM_CATEGORY`, `BUY_SELL_INDICATOR`, plus `SM_UPPER_LIMIT`, `SM_LOWER_LIMIT`, `SM_FREEZE_QTY`. The header ended with an empty trailing field. [Official detailed master](https://images.dhan.co/api-data/api-scrip-master-detailed.csv).
- **D13 — Options:** `POST /optionchain` accepts `UnderlyingScrip`, `UnderlyingSeg`, `Expiry`; `/optionchain/expirylist` returns active expiries for an underlying. Response includes underlying LTP and strike-keyed CE/PE objects: security ID, LTP, average price, volume, previous volume/close/OI, current OI, best bid/ask price/quantity, IV and delta/theta/gamma/vega. Endpoint-specific limit is one unique request per three seconds; documentation permits different underlyings/expiries concurrently on this cadence. [Option chain](https://dhanhq.co/docs/v2/option-chain/).

### Inferences
- Normalized identity is `(broker, segment, security_id, master_version)` mapped to a canonical contract including venue, underlying, expiry, strike and side. Do not join instruments by display text alone or merge NSE/BSE listings merely because the ISIN matches.
- Maintain `source_epoch`, broker, entitlement mode, receive monotonic time, exchange trade time where present, and field-presence bits. Never invent provider publish timestamps, sequence numbers or per-trade IDs for normal packets.
- Market depth must be decoded under a distinct schema from normal full packets. Resolve the bid/ask prose inconsistency with fixtures and real snapshot comparison before enabling depth-dependent trading. Do not use the ignored sequence field to claim lossless gap detection.
- Use REST quotes for initialization and recovery. Heartbeats, subscription health and timestamp plausibility detect stale or suspected gaps; no guaranteed tick replay or gap-free resume is documented.
- Obtain 2/3/10/30-minute candles from locally aggregated one-minute candles. Dhan's 25-minute native interval is not 30 minutes. Higher-timeframe alignment must follow exchange sessions, and locally constructed bars must carry their provenance.
- Enforce option refresh per `(underlying, expiry)` at >=3 seconds, plus conservative account Data API budgets until Dhan confirms category interactions. Retain provider IV/Greeks as provider estimates with snapshot age; calculate PCR, changes, ranking and strategy signals internally.

### Gaps
- No documented normal-feed universal sequence, exchange event identifier, delivery guarantee, resumable cursor or complete trade tape was found. Precise bar reconstruction and exact VWAP from last-trade snapshots cannot be assumed.
- Deep-feed account connection ceiling, whether deep and ordinary connections share the five-connection limit, and entitlement distinctions are not established by the page. Do not multiply 50 or 1 by an invented connection allowance.
- Historical corporate-action adjustment convention, all missing-bar meanings, intraday end-date inclusivity, timestamp timezone parsing and publication lag require validation. Five-year active-instrument history is not a promise of every expired contract's history.
- Index volume/OI/depth may be inapplicable; absent/zero fields need semantic classification. The provided feeds do not establish official sector membership or constituent weights.
- Tick-size, price-band and freeze-quantity units/freshness in the actual master need account fixtures. Do not silently assume that every numeric metadata value is expressed in rupees.

## How should trading, updates, reconciliation and emergency controls use Dhan?

### Takeaway
The APIs cover real order lifecycle, account-wide order streaming and account snapshots. Local idempotency and reconciliation are still required; correlation lookup is not documented server-side deduplication.

### Cited Findings
- **D14 — Order endpoints/contracts:** `POST /orders`, `PUT /orders/{id}`, `DELETE /orders/{id}`, `POST /orders/slicing`, `GET /orders`, `GET /orders/{id}`, `GET /orders/external/{correlationId}`, `GET /trades`, `GET /trades/{orderId}`. Write operations require static IP. Placement fields include client/correlation IDs, side, segment, product, order type, validity, security ID, quantity, prices and optional AMO/BO fields. Correlation IDs allow maximum 30 characters. Types enumerate LIMIT/MARKET/STOP_LOSS/STOP_LOSS_MARKET; validity DAY/IOC. States include TRANSIT, PENDING, PART_TRADED, TRADED, REJECTED, CANCELLED, EXPIRED. Book responses include filled/remaining quantity and average traded price. Cancellation prose says 202/no body while its example includes JSON; support either documented shape. Slicing creates multiple orders over freeze quantity. [Orders](https://dhanhq.co/docs/v2/orders/).
- **D15 — Live order stream:** `wss://api-order-update.dhan.co` sends JSON. Individual login carries `LoginReq.MsgCode=42`, `ClientId`, `Token`, `UserType=SELF`. Stream covers all account orders regardless of originating platform. Update payload contains broker/exchange order IDs, quantities, cumulative traded quantity, remaining quantity, average traded price, times, status, correlation ID and remarks. Field casing differs from REST; samples have malformed JSON/duplicates and require actual contract fixtures. [Live order update](https://dhanhq.co/docs/v2/order-update/).
- **D16 — Postbacks:** HTTP POST JSON is sent on status changes, modification and partial fills. Scope is the access token that originated the orders, unlike the account-wide stream. [Postback](https://dhanhq.co/docs/v2/postback/).
- **D17 — Portfolio:** `GET /holdings` includes T1/delivered quantities. `GET /positions` includes current and F&O carryforward positions with segment, product, net/buy/sell/day/carryforward quantities and values, average prices and realized/unrealized P&L. `POST /positions/convert` converts eligible products. `DELETE /positions` is documented Exit All. [Portfolio and positions](https://dhanhq.co/docs/v2/portfolio/).
- **D18 — Funds/margin:** `GET /fundlimit` returns tradeable balance, start-of-day limit, collateral, receivables, utilized/blocked/withdrawable balances. The actual response spelling is `availabelBalance`. `POST /margincalculator` gives total, SPAN, exposure, variable margin, balance, brokerage and leverage estimates. `/margincalculator/multi` accepts multiple scripts and `includePosition`/`includeOrders`. [Funds and margin](https://dhanhq.co/docs/v2/funds/).
- **D19 — Native protection:** Super orders support entry, target, stop and trailing jump through `/super/orders`; products CNC/INTRADAY/MARGIN/MTF and LIMIT/MARKET entry are documented. Modify/cancel specific legs by broker identifiers. After entry is fully traded only target/stop prices and trailing jump can be changed, whereas entry modifications are restricted to PENDING/PART_TRADED. [Super order](https://dhanhq.co/docs/v2/super-order/).
- **D20 — GTT caution:** Forever order APIs offer SINGLE/OCO at `/forever/orders`; the parameter table documents products CNC/MTF, although some exchange entries are duplicated. Do not assume intraday F&O protection from the generic GTT description. [Forever orders](https://dhanhq.co/docs/v2/forever/).
- **D21 — Emergency controls:** `/killswitch` supports status and activation/deactivation. Activation requires all positions already closed and no pending orders; it is not a liquidation primitive. `/pnlExit` supports configure/read/delete automatic P&L exits; configuration resets after the session. Endpoint payload uses profit/loss values and product selection. [Trader controls](https://dhanhq.co/docs/v2/traders-control/).
- **D22 — Errors:** DH-901 authentication, DH-902 entitlement/access, DH-903 account activation, DH-904 rate throttling, DH-905 input, DH-906 order, DH-907 data, DH-908 server, DH-909 network, DH-910 other. Feed/data codes include 804 capacity, 805 excess requests/connections, 806 unsubscribed, 807 expired, 808/809 invalid authentication, 810 invalid client, 811 expiry, 812 date, 813 security ID, 814 request. [Annexure](https://dhanhq.co/docs/v2/annexure/).

### Inferences
- Durable local intent ID and account-scoped uniqueness must precede submission. Encode a 30-character-safe correlation token and persist mapping. A connection timeout after send creates `SUBMISSION_UNKNOWN`: query by correlation/order, stream and trade book before any retry. Do not presume a repeated correlation ID prevents duplicate orders.
- An ACK is acceptance by an API, not a fill. Cancel acceptance is not proof of zero residual fills. Normalize cumulative quantities and use execution identifiers from trade book for reconciliation; handle fills crossing cancellation/modification.
- Exactly one execution writer per account should own risk reservations and mutations. External manual orders must update positions/risk because the account-wide stream includes them.
- Data failover can change signal provider with a new provenance epoch; it must never migrate Dhan orders or pretend an Upstox position/fund balance belongs to Dhan. An exit must route to the broker/account owning the position.
- Prefer native protective orders only after verifying the exact instrument/product and partial-fill behavior. Local trailing updates require modification-budget accounting, hysteresis and reserved capacity.
- Local emergency sequence: block new entries, cancel pending entries, determine residual positions, submit permitted reducing exits, reconcile actual fills, then optionally activate broker kill switch. If the broker is unreachable, report unresolved exposure and preserve protection rather than claiming success.
- Webhooks require strict schema/account/correlation validation and REST corroboration for uncertain messages. No unverified signature scheme should be invented.

### Gaps
- No documented server idempotency key/guarantee, exactly-once order updates, postback signing protocol, delivery retries/order guarantee, durable event cursor or stream resumption was found.
- Need credential-backed fixtures for status casing, field nullability, exchange/broker timestamp interpretation, partial fills, sliced-child correlation, order-list scope and modification rejects. Samples contain syntax errors and cannot become literal golden payloads unchanged.
- Confirm native Super Order sibling cancellation/partial-fill semantics and protection persistence; do not infer exchange-atomic OCO simply from grouped-order marketing.
- Read-only planning cannot verify margin freshness, per-account product restrictions, market/stop-market permission, static IP activation, broker outage paths or order throughput. These are explicit account acceptance gates before actual live execution.
